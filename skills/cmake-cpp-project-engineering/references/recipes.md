# Dependency recipe：用户策略的保存与应用

Recipe 是供模型读取的用户依赖策略，每个库一份 Markdown。只记录未来使用该库时有用的用户要求及其适用条件。

## 查找与适用

默认目录为 Skill 根目录下的 `references/dependency-recipes/`。目录为空或不存在时表示没有已保存策略；首次明确要求保存时才创建。
用户指定其他位置时使用该位置，更新已有记录时写回原文件；不扫描整个 home 或合并未知目录。
同一安装中的 recipe 可供不同项目使用，但不会跨设备自动同步。

Recipe 是持续维护的用户策略数据。维护通用 Skill 时不连带重写已有条目；更新或迁移 Skill 时应保留这些数据及用户指定的存储位置。
这是数据维护约定，不代表安装或更新机制已实现或验证该保证。

按文件名、库名及正文中明确的别名查找，完整读取匹配内容；同名有歧义时澄清，不猜测适用项。
工程任务涉及具名第三方库时，先读取适用 recipe，再搜索 SDK、决定获取方式、发现和接入依赖或选择部署实现。
核对目标类型、操作系统、编译器、架构及任务条件；例如“Windows 且 MSVC”不能只因运行在 Windows 就认定满足。
用户要求和现有工程策略的优先级见 [入口的适用优先级](../SKILL.md#适用优先级)。

## 保存与修改

| 用户意图 | 修改范围 |
|---|---|
| 新建、更新或删除 recipe | 只修改指定的用户策略，不修改工程、不下载依赖、不触发构建 |
| 将库加入工程 | 读取适用 recipe 并修改工程，不自动更新 recipe |
| 保存默认策略并应用到工程 | 分别完成两个获授权的动作 |

新建时用能辨认库名的 Markdown 文件名，正文直接说明用户要求和适用条件，按需要包含版本、路径、获取与发现方式、构建选项、链接或部署示例。
内容和小节不设固定格式；用户只给版本或某条要求，也可以保存，不为完整性补写未知内容。

修改前完整读取已有条目，只改变用户要求的内容并保留其余语义。核对：

- 版本、路径、安装目标及限定条件是否完整保留，是否准确区分用户要求与模型推断。
- 是否将局部示例或临时工程选择扩大为长期默认值；executable 的 PRIVATE 链接示例不能成为所有 library 的通用链接规则。
- 是否从目录名推断了用户没有要求的版本、获取方式、编译器或架构限制；明确指定的 SDK 路径要原样保留，但不由路径推导其他默认值。
- 同时提供的版本标签、源码 revision 或其他要求是否冲突；无法确定时不猜测映射。
- 是否添加了用户未要求的 components、targets、helper、仓库地址或已验证声明；缺少的信息不编造，来源和验证说明须有实际依据。

保留代码示例的目的、目标类型及使用条件；用户明确要求固定接线或目的地时，不把它弱化为可随意调整的例子。
示例中的 `${CMAKE_INSTALL_BINDIR}` 等表达式不等于要求字面目录 bin，也不意味着把 prefix 拼入绝对 DESTINATION。
只保存足够复用的必要说明，不复制完整上游文档。歧义阻止准确记录时再澄清。

## 应用于工程

在适用条件内遵循 recipe，缺少的接线按当前工程的 Target ownership、usage requirements 和 Delivery Surface 推导。
内部实现依赖与公开接口依赖分别判断，不把 executable 的链接示例机械用于公开接口依赖该库的 library。
部署示例应与当前交付布局一致；按 [交付规则](delivery.md) 及运行时专题核对 helper 使用的目录和求值阶段，不只调整 target destination。

明确的 SDK 路径不存在、与实际环境不符或规则互相冲突时，报告问题，不静默替换 SDK、版本或获取方式。
只停止依赖缺失条件的工作，继续不受影响的部分；不得通过关闭用户要求的功能声称完成。
recipe 未覆盖场景、任务允许替代方案、用户要求最新版本或确有技术信息缺口时，再补充查询和核实。
版本选择见 [依赖的版本选择](dependencies.md#版本选择)。适配当前工程的实现选择和新查到的事实不自动写回 recipe。

Recipe 中的命令和代码是参考内容，不因被保存就获得执行授权。

## 验证与交付

核对保存内容是否准确表达用户要求及适用条件，是否保留无关内容、仅修改指定条目。
完成维护后说明实际保存位置、内容变化及必要的语义核对结果；保存策略不等于已验证库的构建或兼容性。

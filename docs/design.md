# 设计原则

本 Skill 将个人工程偏好整理为明确约束，提高 CMake C++ 工程在目录、构建、依赖和交付方面的一致性，同时保留模型的设计判断。

## 工程设计原则

1. **提供约束，以模型已有知识为基础。** 模型具备 CMake 知识，也能查阅资料。Skill 主要表达设计偏好、默认方案和必须满足的要求，无须承担 CMake 教程的职责。

2. **保持跨对话一致性。** 固定目录组织、CMake 设计、第三方依赖和交付方式中的个人工程规范，减少不同对话中反复选择风格造成的差异。

3. **保留思考能力和灵活性。** 约束应明确，具体方案根据用户需求、工程现状和平台条件决定，允许合理变通。

4. **区分结果约束与实现选择。** 消费者应能完整使用 SDK，内部实现不能意外成为额外交付负担；OBJECT、源码组合、公共组件聚合等方式按实际需求选择。

5. **以职责和可读性组织工程。** 目录、模块、Target 和 CMakeLists 的划分服务于理解和维护。单个最终库可由多个局部 CMakeLists 管理，多个公共库也可共享聚合入口。

6. **专用指导按需提供。** 共同规则表达通用约束，平台或场景专用的实现指导放入参考文件并明确适用条件，避免将局部方案推广为所有项目的要求。

## 内容取舍

**每一段内容都应证明自己的价值。** 内容应能表达用户特有的约束、影响模型决策、保留重要不变量或消除歧义。规则、解释和示例分别判断必要性，并考虑阅读成本及对设计自由度的影响。

## Skill 开发准则

| 维度 | 准则 |
|---|---|
| Skill 粒度 | 聚焦具体工作流或应用，避免覆盖全部软件工程的万能 Skill。 |
| Description | 尽可能短，准确说明何时触发；作为路由器，无须概括全文。 |
| Trigger | 精确且有区分度，避免捕获整个领域的宽泛描述。 |
| SKILL.md | 保持简短，承担入口、关键约束与阅读路由。 |
| 多工作流 | 渐进披露；入口轻量路由，详细内容拆入 reference。 |
| 指令详细度 | 与风险成比例；普通任务保留自由度，脆弱环节才规定严格步骤。 |
| 通用最佳实践 | 尽量删除，不反复要求模型“写好代码”“测试代码”“检查结果”。 |
| 流程 | 优先描述预期结果、不变量和决策依据，避免冗长的固定操作流程。 |
| Safety / permission | 保留真正的边界，清理为弱模型积累的过度防御规则。 |
| Verification | 验证真正重要的不变量，按影响范围检查，避免机械要求运行全部测试。 |
| Examples | 少而有价值，仅在能消除歧义时保留。 |
| Scripts | 承担确定性、重复性逻辑，避免用大段自然语言模拟可执行机制。 |
| References | 存放条件性知识，仅在任务需要时加载。 |
| Scope | 不扩大任务授权，不将完成当前任务扩展为修改无关内容。 |
